# Анализ: гранулярность очередей доставки (этап B)

*Зафиксировано 2026-09-06, чтобы можно было вернуться к рассуждению.*

## Вводные

- **R1 (главная проблема — конвой):** медленный канал (TG_MTPROTO с большим видео)
  держит быстрый (TG_BOT) и следующие события. Решается схемой «очередь на канал +
  воркер на канал» — ЛЮБОЙ из вариантов ниже решает её одинаково.
- **R2 (наблюдаемость):** видеть по логу, что происходит с доставкой.
  Изначально трактовалась максимально («всё ли событие дошло, итог N/M»),
  после обсуждения ослаблена — см. «Развязка».
- **R3 (гигиена):** не портить контракт «сообщения = договорённость
  форматтер↔транспорт» и без причины не отменять принятые решения
  (форматтер до очереди).

## Варианты

### 1. В очереди — сообщения (изначальный дизайн)

Форматтер при постановке; каждая запись очереди — одно готовое сообщение
(альбом/текст), для контекста в логах — конверт `(review_id, msg)`.
Воркер: get → transport → log(review_id, qsize).

- глубина очереди в сообщениях; воркер — чистый транспорт;
- «дошло ли событие целиком» — по отсутствию ошибок / грепом review_id;
- итога N/M нет: некому подвести — событие после dispatch существует
  только как россыпь записей.

### 2. В очереди — уведомления

Запись очереди = notification целиком; форматтер выполняется в воркере;
воркер шлёт все сообщения события и пишет итог «доставлено N/M, провалы: ...».

- владелец события есть → сводка и решения уровня события (break при
  NotAuthorized, будущие ретраи/TTL);
- минус: воркер знает про форматтер, форматтер уехал из dispatch —
  отмена ранее принятого решения.

### 3. В очереди — пакет сообщений события

Запись очереди = `(review_id, [готовые сообщения])`. Форматтер при постановке
(как в 1), владелец события у воркера (как в 2). Синтез: N/M + чистые
контракты + форматтер на месте.

| | 1: сообщения | 2: уведомления | 3: пакет |
|---|---|---|---|
| Конвой (R1) | ✔ | ✔ | ✔ |
| Итог N/M на событие | нет | ✔ | ✔ |
| Форматтер | dispatch | воркер | dispatch |
| Воркер знает про | транспорт | транспорт+форматтер | транспорт |
| Глубина очереди | сообщения | события | события |

## Ошибочный аргумент (зафиксирован, чтобы не повторить)

«В варианте 1 метки review_id/seq замусоривают контракт сообщений» — неверно:
конверт-кортеж `(метки, msg)` в записи очереди решает это без касания сообщений.

## Развязка (решение пользователя)

R2 ослаблено: **ошибки видны в момент отправки** (traceback + список файлов в
тексте ошибок Bot API, а пути файлов содержат review_id) — этого достаточно,
чтобы работать с проблемами. Сводка «N/M» — избыточная бухгалтерия:
нет ошибок в логе = дошло всё. Что реально важно от очередей — **заполненность**
(сигнал «канал не успевает»).

С ослабленным R2 преимущества вариантов 2/3 (владелец события ради сводки)
теряют смысл → **выбран вариант 1**: готовые сообщения в очереди,
конверт `(review_id, msg)` для контекста логов, qsize в строках
постановки/доставки, warning при заполнении очереди.

Если когда-нибудь понадобится логика уровня события в доставке
(ретраи целиком, TTL, дедупликация) — возвращаемся сюда и переезжаем
на вариант 3: это смена формы записи очереди, а не архитектуры.
